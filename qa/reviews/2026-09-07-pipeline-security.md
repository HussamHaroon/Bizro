## Findings

### F1 — `[P0 demo-breaking trust]` credit-agent/credit_agent/report.py:216 — persisted report_json STRIPS the mock marker; mock reports present as real from the DB
- **Evidence:** `report.py:207-208` sets `report["mock"] = True` when the narrative ran without a live model; line 216 persists `report_json={k: v for k, v in report.items() if k not in ("mock",)}` — the marker is deliberately deleted from the stored row. Reproduced live on a scratch DB: returned dict has `mock: True`, the persisted `credit_reports.report_json` has **no** `mock` key. Every consumer that loads the row (dashboard cached preview `server/app/api.py:1025`, seed_demo rows via `credit-agent/scripts/seed_demo.py:108`, any committee/officer tool reading rows) then renders a template-narrative report with attribution "Generated by qwen-flash via Alibaba Cloud Model Studio" (`render.py:219-227` claims this from `report["model"]`, which is set unconditionally at `report.py:109`) — a model run that never happened. This contradicts schema.md §6.3/§6.11 ("mock marker … when persisted it lives at source.raw_output.mock"; "the persisted raw_model_output carries mock: true") and contradicts the server's own adoption path, which deliberately keeps the key: `server/app/api.py:1170` `adopted.report_json = report  # keep mock/generator keys (§6.3)`. A judge clicking a cached report for a mock-seeded merchant sees fabricated provenance — the exact "mock presented as real" failure the skill forbids.
- **Smallest safe fix:** stop stripping — persist `report_json` with the `mock` key included. No consumer reads `report_json` expecting the key's absence (server tests assert its *presence* on the fallback path, `server/tests/test_fix_block.py:452`).

### F2 — `[P1 trust/labeling]` credit-agent/credit_agent/committee_summary.py:229-282 — committee one-pager renders NO mock banner (§6.3 violation on the highest-stakes surface)
- **Evidence:** `render.py:474-477` renders `<div class='mock'>MOCK DATA — …</div>` when `report.get("mock")`; `committee_summary.py` has no `mock` handling at all (no `report.get("mock")` anywhere in the file). The committed artifact proves it: `credit_report_demo.html:76` carries the banner, `credit_report_committee.html` has **0** matches for "MOCK DATA". A mock report's committee pack shows the AI-PARSED stamp, a corroboration headline and a sealed-chain QR with no synthetic-data disclosure — schema.md §6.3: "Dashboard/report layers must surface a 'mock data' banner whenever the marker is present."
- **Smallest safe fix:** render the same red mock band at the top of the committee sheet when `report.get("mock")` is truthy; one test asserting banner presence/absence.

### F3 — `[P1 incorrect user-visible result]` credit-agent/credit_agent/aggregates.py:119-122 — provenance mix drops `source_type="text"` entries; the report contradicts itself on the same page
- **Evidence:** `aggregates.py:119-121` counts only `voice|photo|manual`, so typed entries (`source_type="text"`, a live pipeline output — `voice-agent/voice_agent/models.py:51`, DB CHECK accepts it) appear in **no** metrics provenance bucket; the three displayed percentages sum below 100%. Meanwhile `data_quality.py:158` counts `manual` as `manual + text`. Reproduced live: 5 voice + 5 text entries → metrics provenance `voice 50.0 / photo 0.0 / manual 0.0` while the data-quality card on the same report prints `manual 50.0`. The demo seeder guarantees this is visible: `credit-agent/credit_agent/seed.py:228-230` inserts a typed sale "most days".
- **Smallest safe fix:** count `text` inside the `manual` bucket in `compute_aggregates` (one-line change, matches the data-quality definition exactly). No test pins the old split.

### F4 — `[P1 reliability/security]` voice-agent/voice_agent/models.py:23-43,67 — model-extracted strings have NO length caps; a garbled/hostile note can break the WhatsApp confirmation and flood the DB
- **Evidence:** `Counterparty.name`, `ItemLine.item`, `ItemLine.unit`, `Transaction.description`, `RawOutput.transcript` accept unbounded strings. The confirmation echoes them verbatim (`confirmation.py:248-253` item read-back, `_KIND_TEMPLATES` name interpolation) — a model echo of a noisy note can push `confirmation_ur` past WhatsApp's 4096-char message cap, the outbound send fails, and the merchant gets **no reply** (§6.9 violation) — while the DB row stores megabytes. bizro-security SKILL.md: "OCR/voice-extracted strings (names, items) are length-capped by the contract" — no such cap exists anywhere (server `schemas.py` has none either). `RawOutput` keeps `extra="allow"` so a hostile "transcript" of any size is stored as-is (`pipeline.py:512`).
- **Smallest safe fix:** `max_length` caps at the contract models (name 120, item 120, unit 24, description 500) so over-long model garbage routes to the EXISTING graceful paths (voice: `ValidationError` → low-confidence clarification, `pipeline.py:535-541`; never a guess), plus a truncating validator on `RawOutput.transcript` (audit echo, safe to cap at 4000). One test per family.

### F5 — `[P1 reliability/security]` vision-agent/vision_agent/schemas.py:30-37,57-73 + pipeline.py:156 — same missing caps on the OCR surface, plus unbounded model text stored in raw_output
- **Evidence:** `ExtractedItem.item`/`unit` and `ReceiptExtraction.supplier_name`/`bill_number`/`supplier_phone`/`unclear_parts` are uncapped; a hostile/garbled receipt can inject arbitrarily long "printed" strings that flow into `confirmation_ur` (`urdu.py:56-70`) and `counterparty.name`/`description` (`pipeline.py:140-172`) — same WhatsApp-send failure mode as F4. `pipeline.py:156` stores the verbatim model answer (`model_response_text: result.raw_text`) with no bound — a runaway OCR answer lands whole in `transactions.raw_model_output`.
- **Smallest safe fix:** `max_length` on the extraction fields (item 120, unit 24, supplier 200, bill 64, phone 32) — over-long items are ALREADY dropped gracefully per-line by `_drop_unreadable_items` (`schemas.py:97-123`); cap `unclear_parts` notes at 200 in `_coerce_unclear`; truncate `raw_text` to 8000 chars where it is stored. One test.

### F6 — `[P1 demo-breaking reliability]` vision-agent/vision_agent/pipeline.py:87 (+ dashscope_client.py:51-76) — an unreadable/oversized image leaves the merchant with NO reply (§6.9), unlike every other bad-input path
- **Evidence:** `image_to_data_url` raises `ImageError` for missing/empty/oversized/unsupported files (`dashscope_client.py:62-75`); the real adapter lets it propagate (`adapters.py:58-96`); `process_receipt_image` catches nothing (`pipeline.py:87`). On the webhook, `ImageError` is neither a rejection (no `reply_ur` attribute) nor an outage (not in `_OUTAGE_EXC_NAMES`, `server/app/dispatch.py:699-709`) → `webhook.py:576-590` re-raises it → per-message guard swallows it → **silence**. A mere blur gets the polite "please resend" (`ReceiptRejected`, `pipeline.py:92-104`); a corrupt download or a big photo gets nothing. §6.9: "clarification, never silence."
- **Smallest safe fix:** in `process_receipt_image`, catch `ImageError` around `adapter.extract` and re-raise `ReceiptRejected("unreadable", reject_reply_ur("unreadable"))` — rides the blessed §6.4 rejection path end-to-end with zero server changes. One test.

### P2 / ROADMAP (reported, deliberately NOT fixed this pass)

- `[P2]` voice-agent/voice_agent/invoice.py:478-481 — `_default_out_path` interpolates `source.media_id` into the filename unsanitized (`invoice_{ref}_{stamp}`); a non-UUID id could traverse out of `media/invoices/`. Defense-in-depth only: the production caller passes a server-UUID path (`server/app/api.py:452-454`). Fix: sanitize `ref` to `[A-Za-z0-9_-]` (ROADMAP — one line, needs its own test cycle).
- `[P2]` vision-agent/vision_agent/dashscope_client.py:64-66 — image MIME resolved from file extension, not magic bytes (skill: "validate magic bytes, not extensions"). Bounded impact: PIL re-opens for EXIF, model API is the only consumer. ROADMAP.
- `[P2]` voice-agent/voice_agent/decode.py:50 — no size cap on `decode_audio` input (WhatsApp caps 16MB server-side; the local pipeline itself is unbounded). ROADMAP.
- `[P2]` credit-agent/credit_agent/narrative.py:82-100 — reasoning-model call sets no `max_tokens`; a runaway answer lands in the narrative (timeout 30s bounds it, length does not). ROADMAP.
- `[P2]` credit-agent/credit_agent/db_view.py:97-102 + committee_summary.py:62-80 — `get_sessionmaker`/`chain_tail` build a new SQLAlchemy engine per call and never dispose it (connection churn on repeated renders). ROADMAP.
- `[P2]` voice-agent/voice_agent/stt_client.py:121 — byte-identical primary/secondary transcripts skip the crosscheck record entirely (`transcript != secondary` guard), so a true 1.0-agreement gets no §8 bonus and no audit record. Behavior is conservative (never wrong, just unboosted). ROADMAP.
- `[ROADMAP]` voice-agent/voice_agent/pipeline.py:419 — entries-per-note unbounded; a model returning 1000 transaction objects would fan out 1000 assembly cycles (needs a contract ruling on a max-entries cap).
- `[ROADMAP]` Cross-surface numeral cosmetics: vision `urdu.py:52` uses thousands separators (`1,200.50`), voice `confirmation.py:24-32` does not (`1200.5`). Consistent within each message; unify only with a UX ruling.

## Verified-good (evidence for the PASS rows)

- **Prompt injection cannot alter control flow:** kind is Literal-validated (`voice models.py:18`, `vision schemas.py:165-171`); amounts route through `_safe_amount` (`pipeline.py:661-672`, null → clarification, §6.2); `unclear` is consulted only via membership tests (`pipeline.py:487,500-510`); JSON extraction is fenced/brace-scanned parsing only (`pipeline.py:625-641`, `parsing.py:30-76`); a receipt saying "ignore previous instructions" lands as item text — escaped or plain-text echo, never executed or re-prompted as a system message.
- **Escaping complete on all three HTML surfaces:** invoice escapes merchant (`invoice.py:301`), counterparty (`:308,310`), item names (`:332`), media ref (`:388`); report escapes every payload string via `_esc` (`render.py:89-90`, applied at `:243-309,320-471,492-517`); committee escapes every payload string (`committee_summary.py:122-181,231-280`). Attribute contexts use double quotes with escaped values (single quotes are escaped too by `html.escape` default `quote=True`). The only raw interpolations are repo-trusted tokens (`tokens.json`) and internal constants.
- **Secrets:** grep across the three packages finds no key material in logs/fixtures/screenshots; `DashScopeError` bodies are provider responses (`dashscope_client.py:97-102`); Authorization headers are built per-call and never logged.
- **ffmpeg subprocess:** argv-list invocation, no `shell=True`, fixed temp filenames (`in.bin`/`out.wav`), `timeout=120`, stderr truncated to 300 chars (`decode.py:96-114`) — no filename injection surface (bytes are written to a fixed path).
- **Mock labeling on transaction surfaces:** voice sets BOTH `mock: true` top-level and `raw_output.mock` (`pipeline.py:513-514,588-589`, `models.py:74`); vision sets `raw_output.mock` + `source.model="mock:<id>"` (`pipeline.py:162-164`, `adapters.py:135`); the invoice PNG/text both render the MOCK band (`invoice.py:357,428-429`); the server re-derives the top-level banner for wire rows from `raw_model_output.mock` (`server/app/api.py:418`).
- **Outage handling on voice/credit:** corrupt audio → clarification envelope (`pipeline.py:211-224`); structuring outage → typed `DashScopeError` → server busy reply (`pipeline.py:203-210`); credit narrative outage → deterministic template, report never blocked (`narrative.py:105-106`).
- **Audit trail:** every credit line item carries the four §6.5 audit fields (`report.py:174-185`); red flags carry refs or an honest reason (`report.py:122-138`); forensics/data-quality are disclosures with a basis note (`data_quality.py:186-192`).
